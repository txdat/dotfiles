# TDD Proof — Single Source

Used by execute-feature and approved-plan fix-bug execution; independently verified by review-code. The approved spec owns the oracle (`Goal → AC → TC`); TDD owns implementation proof (`approved TC → RED → GREEN → BLUE`).

1. Implement each approved TC exactly: Given → setup, When → call, Then → assertion; confirm the assertion proves its named AC and observable Goal outcome. Do not invent, merge, split, or reinterpret behavior.
2. Refactor: confirm the behavior test passes before change — the rest of this step is feature/fix only. Feature/fix: obtain each new test's result and failure reason. A targeted batch is valid when it identifies every test and its outcome; an aggregate exit code is insufficient. Rerun tests separately when output is ambiguous, tests were skipped or never reached, or isolation problems could explain the result. A needed stub may only throw/panic/not-implemented; it must not return the expected value. Three mechanical rules:
   - **Baseline evidence.** Where the production path exists, run against its unchanged parent commit. A new test that already passes does not prove the missing behavior; investigate its arrangement and intended delta. Where a genuinely new API needs a throwing stub to compile, confirm the test reaches that stub and fails. Record this as provisional invocation evidence, commit tests and stub in step 3, and complete behavioral proof in step 4. A stub-only failure never establishes the scenario's behavioral sensitivity.
   - **Fails for the right reason.** Read each failure. Missing imports, broken fixtures, and typos require correction before proof; they do not establish missing behavior. Existing-path tests must fail for the named missing behavior. Only the new-API stub case above may defer that determination until step 4.
   - **Unconstructible arrangement is an AC defect, not a free reinterpretation.** If the scenario cannot be built — the runtime re-pins the input, two ACs demand contradictory states — STOP and return through `approval.md`. Substituting a scenario you *can* build silently replaces approved behavior.

   Record the per-test baseline and any pending behavioral check. Constructibility and behavioral sensitivity must be established before GREEN is committed; review-code independently checks the evidence and remaining assertion/contract defects.
3. Before implementation, commit tests alone: `test(red): <scope>` for feature/fix or `test: baseline <scope>` for refactor. Explicitly named throwing stubs are permitted; no plan or implementation files. Record which new-API tests still need step 4's behavioral check. On resume, inspect evidence and pending checks rather than trusting the commit title.
4. Implement the approved behavior and run targeted tests. For each pending new-API check, the main agent performs **GREEN-minus-one**: confirm the test passes, temporarily disable only its named behavior, and confirm that test fails for the corresponding assertion. Restore the implementation after each check regardless of the result, inspect the diff for leftover mutations, and rerun affected tests on the restored code. A test that stays green needs repair within its approved intent and another sensitivity check; do not weaken the expected outcome to force failure. A delegated reviewer inspects this evidence and reports gaps; it never mutates production code to create it. Commit GREEN separately only when tests pass on the restored implementation and all pending checks are resolved. Correct all valid inputs and satisfy the parent AC; canned test-specific answers remain forbidden.
5. BLUE is a quality pass, not mandatory code churn: inspect the GREEN implementation, refactor only when it improves the design, and keep tests green. Rerun targeted tests and coverage for any BLUE-touched files; "no refactor needed" is valid.

Ambiguity or contradiction among Goal, AC, TC, another TC, observed contract, or domain source → STOP before changing test or implementation, and go back through `approval.md`. TDD never decides new behavior.

Run `~/.dotfiles/.ai-shared/bin/dev-check proof <commit> [--test <in-source-test-path>] [--stub <throwing-stub-path>]` before GREEN and during review. It validates paths and blocks obvious value-return stubs; inspect allowed paths and the test's behavioral assertion yourself.

**Its strictness is real, but you choose its scope.** An undeclared non-test path blocks outright; a `--stub` path is scanned for value returns and body-less forms that return implicitly; a `--test` path must add recognizable test code. Two gaps remain by construction: conventional test paths (`tests/`, `*_test.*`, etc.) are skipped whole, and a `--test` file adding production code beside a test passes on the test's presence. Classify honestly and read the bodies yourself. A `PASS` means the declared paths are acceptable, never that the commit is implementation-free.
